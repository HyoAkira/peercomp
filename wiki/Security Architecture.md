## Security Architecture

Relevant source files

The PeerComp security architecture implements a defense-in-depth strategy across the entire stack, from network-level TLS termination to sandboxed user code execution. It ensures data confidentiality through end-to-end encryption (E2EE) for storage and maintains system integrity via strict JWT-based authentication and SSRF protection.

## Authentication and Authorization

PeerComp uses a JSON Web Token (JWT) flow to secure access to the Org API and the user dashboard.

- Token Issuance: The in the app generates JWTs upon successful login.
- Token Verification: Protected routes are guarded by the middleware, which extracts the Bearer token from the header and populates.
- Frontend Enforcement: The component checks for token existence and expiration on the client side, redirecting unauthorized users to the login page.
- API Usage: Client-side components like retrieve the token from the Zustand store to authorize requests [apps/web/app/pages/panel/components/deleteModal.tsx#10-20](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/pages/panel/components/deleteModal.tsx#L10-L20)

For details, see [Authentication and Authorization](#6.1).

## End-to-End Encryption for KV Storage

To ensure privacy in a distributed environment, the Key-Value (KV) storage system employs client-side encryption before data reaches the network or the database.

- Key Agreement: Uses ECDH (P-256) for generating shared secrets between nodes.
- Identity Verification: Uses ECDSA signatures to sign public keys, preventing Man-in-the-Middle (MITM) attacks during key exchange.
- Data Encryption: Values are encrypted using AES-GCM (256-bit) with a unique Initialization Vector (IV) for every entry.
- Offloading: All cryptographic operations are offloaded to a Web Worker to prevent blocking the main UI thread [memory-bank/activeContext.md#56-57](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/memory-bank/activeContext.md?plain=1#L56-L57)

For details, see [End-to-End Encryption for KV Storage](#6.2).

## Sandboxed Code Execution

User-defined serverless functions are executed within a highly restricted environment to prevent malicious code from compromising the host. This environment is shared between the browser-based worker and the Node.js gateway.

- Hardening: Both (browser) and (Node.js) invoke from the package with strict taming settings [apps/web/app/lib/peer/worker.js#3-6](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L3-L6) [apps/node-worker-gateway/worker.mjs#4-7](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/node-worker-gateway/worker.mjs#L4-L7)
- Isolation: Execution is handled by from the package, which utilizes SES Compartments [apps/web/app/lib/peer/worker.js#57-58](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L57-L58) [apps/node-worker-gateway/worker.mjs#13-14](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/node-worker-gateway/worker.mjs#L13-L14)
- SSRF Protection: The utility filters hostnames to block access to, private IPv4 ranges (e.g.,, ), and private IPv6 ranges [apps/web/app/lib/peer/worker.js#12-49](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L12-L49)
- Resource Control: Execution is bounded by a default 15-second timeout to prevent denial-of-service via infinite loops [apps/web/app/lib/peer/worker.js#53](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L53-L53) [apps/node-worker-gateway/worker.mjs#11](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/node-worker-gateway/worker.mjs#L11-L11)
