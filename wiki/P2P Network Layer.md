## P2P Network Layer

Relevant source files

The P2P Network Layer is the backbone of the PeerComp platform, enabling decentralized communication, distributed key-value storage, and serverless compute execution across browser-based and server-side nodes. It leverages the Kademlia Distributed Hash Table (DHT) protocol for routing and discovery, and WebRTC (via PeerJS) for peer-to-peer data transmission.

The network consists of three primary entities working in concert:

1. PeerSignal Server: Facilitates the initial WebRTC handshake (signaling) and peer discovery.
2. Browser KademliaNode: Client-side participants that store data and execute functions.
3. GatewayNode: Server-side participants that provide stable network presence and sandboxed execution environments.

## 4.1 PeerSignal Signaling Server

The PeerSignal server is a specialized signaling service built on the library. It performs two critical roles:

- WebRTC Signaling: Acting as a STUN/Signaling intermediary, it allows peers to exchange SDP (Session Description Protocol) and ICE candidates to establish direct P2P connections [apps/peer\_signal/peer-signal.ts#14-18](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/peer_signal/peer-signal.ts#L14-L18)

## 4.2 Browser KademliaNode

The KademliaNode is the browser-resident implementation of the DHT. Every user visiting the PeerComp web application becomes a node in the network. It uses a 256-bit ID space [apps/web/app/lib/peer/peer-node.ts#9](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/peer-node.ts#L9-L9) and calculates logical distance between nodes using the XOR metric [apps/web/app/lib/peer/peer-node.ts#23-29](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/peer-node.ts#L23-L29)

Key features include:

- Routing Table: Managed via objects that store references to other peers in buckets of size $K=20$ [apps/web/app/lib/peer/peer-node.ts#7-67](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/peer-node.ts#L7-L67)
- Hybrid Storage: Uses a that transparently bridges in-memory caching with IndexedDB (Dexie) for persistent storage of functions and KV pairs [apps/web/app/lib/peer/peer-node.ts#102-222](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/peer-node.ts#L102-L222)
- Distributed RPCs: Supports standard Kademlia operations (, ) and custom extensions like for distributed execution [apps/web/app/lib/peer/peer-node.ts#41-63](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/peer-node.ts#L41-L63)

For details, see [Browser KademliaNode (apps/web)](#4.2).

## 4.3 GatewayNode and Worker Execution

The GatewayNode is a Node.js-based participant designed to provide high availability and secure execution environments. It utilizes for WebRTC [apps/node-worker-gateway/node.ts#14](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/node-worker-gateway/node.ts#L14-L14) and for data serialization [apps/node-worker-gateway/node.ts#17](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/node-worker-gateway/node.ts#L17-L17) to maintain compatibility with PeerJS clients.

The GatewayNode's primary responsibility is handling RPCs. When a function execution is requested, the Gateway dispatches the task to a SES (Secure EcmaScript) sandbox running in a Worker Thread [apps/node-worker-gateway/node.ts#16](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/node-worker-gateway/node.ts#L16-L16) This ensures that user-provided code is executed in an isolated environment with restricted access to system resources and network APIs.

For details, see [GatewayNode and Worker Execution (apps/node-worker-gateway)](#4.3).
