## Sandboxed Code Execution

Relevant source files

The PeerComp platform executes user-defined serverless functions within a highly restricted environment to ensure the security of the host node and the integrity of the distributed network. This is achieved using Secure EcmaScript (SES) within Node.js worker threads and browser Web Workers, combined with strict SSRF (Server-Side Request Forgery) protections and API blocking.

## Sandbox Architecture Overview

Code execution is triggered when a RPC is received or when an HTTP request hits the gateway's Express server. The execution logic is centralized in the package, which is consumed by both the server-side gateway and the browser-side worker.

### The Execution Lifecycle

1. Request Handling: The system identifies the function code from the local database or DHT.
2. Worker Spawn: A new Node.js (in ) [apps/node-worker-gateway/worker.mjs#3](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/node-worker-gateway/worker.mjs#L3-L3) or a browser Web Worker (in ) [apps/web/app/lib/peer/worker.js#1-2](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L1-L2) is utilized.
3. Hardening: The worker immediately invokes from the library to freeze JavaScript intrinsics [apps/web/app/lib/peer/worker.js#3-6](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L3-L6)
4. Compartmentalization: The function creates a new SES to evaluate user code with its own global scope [packages/worker/index.js#20-24](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/packages/worker/index.js#L20-L24)
5. Timeout Enforcement: The calling thread monitors the worker and terminates it if execution exceeds the default 15-second timeout [apps/web/app/lib/peer/worker.js#53](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L53-L53)

## SES Hardening and lockdown()

The sandbox relies on the library to transform the environment into a "Secure EcmaScript" realm.

## Execution Constraints

To maintain system stability, the sandbox enforces several runtime limits:

- Time Limit: Every worker execution is wrapped in a 15,000ms (15 seconds) timer [apps/web/app/lib/peer/worker.js#53](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L53-L53)
- Argument Injection: User arguments are passed into the sandbox as a read-only global object [packages/worker/index.js#46-51](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/packages/worker/index.js#L46-L51) These are hardened using before injection [packages/worker/index.js#61](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/packages/worker/index.js#L61-L61)
- Code Sanitization: Before execution, the code is trimmed and normalized to ensure consistent parsing [apps/web/app/lib/peer/worker.js#8-11](https://github.com/HyoAkira/bitirme2/blob/7a5d8555/apps/web/app/lib/peer/worker.js#L8-L11)
